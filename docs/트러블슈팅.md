# 트러블슈팅 기록

겪은 문제와 해결. 같은 문제를 두 번 겪지 않기 위한 기록.

---

## 1. `-parameters` 컴파일 옵션 — `@PathVariable`, `#{}` 바인딩 실패

**증상** — Spring 7.0 / MyBatis 조합에서 매개변수 이름이 사라져 `@PathVariable`과 MyBatis `#{}` 바인딩이 실패.

**원인** — 자바는 컴파일 시 파라미터 이름을 버려 바이트코드에 `arg0`, `arg1`만 남음. Spring 6.1+부터 `-parameters` 없이는 이름 추론을 하지 않음.

**해결** — `-parameters` 옵션을 **`build.gradle`과 STS Preferences 양쪽** 다 켜야 해결. 한쪽만 켜면 로컬은 되는데 CI에서 터지거나 그 반대.

**교훈** — MyBatis 매퍼 파라미터가 2개 이상이면 `@Param`을 붙여 컴파일 옵션 의존을 없애는 게 안전.

---

## 2. Spring Boot welcome page가 Security와 충돌

**증상** — static `index.html`을 welcome page로 두고 `permitAll("/")`을 넣어도 401.

**해결** — `@GetMapping("/")` 컨트롤러(`RootController`)로 우회. `/views/main.html`로 리다이렉트.

---

## 3. 에러 페이지에서 CSS 404

**증상** — 404/500 에러 페이지의 CSS가 안 먹음.

**원인** — 에러 페이지는 forward라 URL이 원래 요청 주소에 머무름. CSS를 상대경로로 걸면 그 주소 기준으로 찾아서 404.

**해결** — 절대경로 필수.

---

## 4. `authGuard`의 상대경로가 폴더 깊이에 따라 깨짐

**증상** — `'user/login.html'` 같은 상대경로가 `/views/personal/` 깊이의 페이지에서 깨짐.

**해결** — 절대경로로 수정. 이후 프로젝트 전체 원칙으로 확정 (ADR-033).

## 5. 미분류 자동생성 시 순환참조

**증상** — `UserService`가 `PersonalCategoryService`를 주입받으면 순환참조 위험.

**해결** — `UserService.signup()`에서 `PersonalCategoryMapper`를 직접 주입. `@Transactional`로 묶고 롤백 테스트까지 확인.

**교훈** — Service가 다른 도메인의 데이터를 건드릴 땐 그 도메인의 Service가 아니라 Mapper를 직접 주입하는 패턴. 카테고리 삭제 시 거래 이관에도 동일하게 적용 (ADR-023).

## 6. macOS 사이드카 — 디스플레이가 데스크탑 1로 합쳐짐 (개발 환경)

**증상** — 재부팅 후 맥북·아이패드가 각각 데스크탑 1·2였던 게 하나로 합쳐지고 세 손가락 스와이프가 안 됨.

**원인** — 시스템 설정 → 데스크탑 및 Dock → Mission Control → "각각의 Spaces가 있는 디스플레이"가 꺼짐.

**해결** — 토글을 켜고 **재부팅** (로그아웃만으론 앱이 취소시킬 수 있음). 터미널 강제 적용:
```
defaults write com.apple.spaces spans-displays -bool false && killall SystemUIServer
```
사이드카 목록에 iPad가 안 뜨면 USB-C 케이블로 직접 연결하면 즉시 뜸.

## 7. 캐치올 예외 핸들러가 스프링의 4xx 를 500 으로 덮어씀

**증상** — 필수 쿼리파라미터(`?year=`, `?version=`)를 빼고 호출하면 400 이 아니라 **500 "서버 오류가 발생했습니다"** 가 나감.

**원인** — 스프링이 던지는 `MissingServletRequestParameterException` 에 대응하는 핸들러가 없어서,
`GlobalExceptionHandler` 맨 아래의 `@ExceptionHandler(Exception.class)` 캐치올이 삼켜버림.
클라이언트 실수인데 서버 잘못이라고 응답하는 꼴.

**해결** — 전용 핸들러 추가. 어떤 파라미터가 빠졌는지도 함께 응답.
```java
@ExceptionHandler(MissingServletRequestParameterException.class) → 400
```

**교훈** — 캐치올 핸들러가 있으면 스프링이 원래 4xx 로 처리해줬을 MVC 예외까지 전부 500 이 된다.
새 API 를 만들 때마다 "이 요청이 잘못되면 어떤 예외가 나는가"를 한 번씩 확인할 것.
(`MethodArgumentTypeMismatchException` 은 이미 등록되어 있었지만 이건 빠져 있었다)

## 8. QA 스크립트 — 중첩 명령치환에서 curl body 유실 (macOS /bin/sh)

**증상** — 같은 요청인데 어떤 케이스는 201, 어떤 케이스는 400 "요청 형식이 올바르지 않습니다".

**원인** — macOS `/bin/sh`(bash 3.2 POSIX 모드)에서 아래처럼 중첩하면 본문이 유실됨.
```bash
check 3 201 "$(req POST /path "{\"a\":1}")"   # ✗ body 가 사라짐
```
변수에 먼저 담은 케이스만 통과해서 원인을 찾는 데 두 번 헛발질했다.

**해결** — 중첩을 없앰. 본문은 항상 `B=...` 변수에 담고, 요청+판정을 한 번에 하는 `t()` 헬퍼 사용.

**교훈** — 기대 상태코드와 실제 실패 코드가 같으면(둘 다 400) **가짜 통과**가 난다.
상태코드만 보지 말고 응답 body 도 검사할 것.

## 9. 정리 스크립트가 자기참조 FK 에 막힘 — 2계층 카테고리를 처음 만든 뒤

**증상** — 여태 잘 돌던 `qa/reset-data.sql` 이 갑자기 실패.
```
ERROR 1451: Cannot delete or update a parent row: a foreign key constraint fails
(`dotoree`.`personal_categories`, CONSTRAINT `FK_PCAT_PARENT` ...)
```

**원인** — `DELETE FROM personal_categories WHERE is_default_yn = 'N'` 한 문장으로
부모와 자식을 같이 지우려 했다. MySQL 은 한 DELETE 안에서 행 삭제 순서를 보장하지 않으므로,
부모가 먼저 지워지는 순간 자식이 아직 그 부모를 참조해 FK 위반.

그전까지 안 걸린 이유는 **QA 스크립트가 2계층 카테고리를 만든 적이 없었기 때문**이다.
`test-category-transfer.sh` 의 케이스 11(자식 있는 대분류 삭제 → 400)이 처음으로
부모-자식 쌍을 실제로 만들면서 드러났다.

**해결** — 소분류 → 대분류 순서로 두 문장으로 나눔. 2계층 제한(ADR-019)이라 두 번이면 충분.
```sql
DELETE FROM personal_categories WHERE is_default_yn = 'N' AND parent_category_num IS NOT NULL;
DELETE FROM personal_categories WHERE is_default_yn = 'N';
```
`reset-all.sql` 은 `SET FOREIGN_KEY_CHECKS = 0` 으로 감싸 이 문제가 없다.
부분 삭제 스크립트에서 FK 체크를 끄지 않은 이유는, 껐다가 '미분류' 를 잘못 지워도
DB 가 막아주지 못하기 때문. 전체 삭제와 부분 삭제는 안전 장치를 다르게 둔다.

**교훈** — QA 케이스가 늘면 **테스트 데이터의 모양**도 늘어난다.
문서에만 있던 제약(2계층)을 처음 실제로 만들어보는 순간, 그 제약을 고려하지 않은
주변 스크립트가 깨진다. 기능 QA 를 추가하면 정리 스크립트도 한 번 돌려볼 것.

## 10. AI 에게 커밋을 맡기면 `.git` 에 잠금 파일이 남는다 (개발 환경)

**증상** — AI(원격 작업 환경)가 커밋한 뒤 맥에서 `git commit` 하면
`Unable to create '.git/HEAD.lock': File exists`. 예전엔 `git status` 만으로 `.git/index.lock` 이 남은 적도 있다.

**원인** — AI 의 작업 환경은 연결된 폴더에 **쓰기는 되지만 삭제 권한이 없다.**
git 은 커밋 중 `HEAD.lock`·`objects/maintenance.lock`·`objects/*/tmp_obj_*` 를 만들었다가 지우는데, 지우기가 막혀 찌꺼기로 남는다.
커밋 자체는 정상으로 끝난다 (`warning: unable to unlink ... Operation not permitted` 가 그 신호).

**해결** — 맥 터미널에서 한 번.
```bash
rm -f .git/HEAD.lock .git/index.lock .git/objects/maintenance.lock
find .git/objects -name 'tmp_obj_*' -delete
```

**규칙**
- AI 의 git **조회**는 `git --no-optional-locks ...` 로 (잠금 파일을 만들지 않는다)
- AI 에게 **커밋**을 맡기면 위 정리를 한 번 해야 한다. 작성자 정보도 없어서 `-c user.name=... -c user.email=...` 지정이 필요. 번거로우면 커밋은 직접, AI 는 메시지 제안만
- 푸시는 항상 직접

## 11. `reset-all.sh` 가입 400 — 원인이 안 보인다

**증상** — DB 를 재생성하고 `sh qa/reset-all.sh` 를 돌리자 초기화는 되는데
`❌ 가입 실패 test@test.com (400)` 만 반복. 상태 코드뿐이라 무엇이 틀렸는지 알 수 없다.

**원인** — `QA_PASSWORD` 에 EC2 DB 용으로 만든 `openssl rand -base64 24` 값이 들어 있었다.
24바이트를 base64 로 바꾸면 **정확히 32자**라 `SignupRequestDto` 의 `@Size(min=8, max=20)` 에 걸린다.

**왜 찾기 어려웠나** — `signup()` 이 `curl -s -o /dev/null -w "%{http_code}"` 라
**응답 본문을 버린다.** 서버는 "비밀번호는 8자 이상 20자 이하로 입력해주세요." 를 내려주고 있었는데 화면에 안 나왔다.

**해결** — 원래 테스트 비번으로 되돌린다. 원인을 볼 때는 본문을 직접 본다.
```bash
curl -i -X POST http://localhost:8080/api/users/signup \
  -H "Content-Type: application/json" \
  -d "{\"email\":\"test@test.com\",\"password\":\"$QA_PASSWORD\",\"nickname\":\"테스트\"}"
```

**규칙**
- **운영 비밀값과 QA 비밀값을 섞지 않는다.** `QA_PASSWORD` 는 가짜 계정용이고 나중에 CI 전용 값이 된다.
  EC2 DB 비번은 `EnvironmentFile` 용이다
- 스크립트가 실패를 보고할 땐 **상태 코드만 찍지 않는다** — 4단계 `_lib.sh` 작업에 반영
- 셸에서 `mysql -u root -p -e "..."` 를 여러 줄로 붙여넣다 `dquote>` 가 뜨면 따옴표가 안 닫힌 것.
  `Ctrl+C` 로 취소하고 **한 줄로** 다시 붙여넣는다 (아무것도 실행되지 않은 상태다)

## 12. EC2 첫 기동 — 테이블은 19개인데 `Table 'dotoree.users' doesn't exist`

**증상** — 1차 배포 2-5. Flyway 가 `Successfully applied 1 migration` 을 찍고 `information_schema` 로 세어도 19개인데,
가입 API 가 500(고정 문구 "서버 오류가 발생했습니다."). 로그 마지막에
`Caused by: java.sql.SQLSyntaxErrorException: Table 'dotoree.users' doesn't exist`

**원인** — 테이블 이름 대소문자. `SHOW TABLES` 는 `USERS`, 앱이 찾는 건 `users`.
`lower_case_table_names` 가 맥은 `2`(비교 시 무시), 리눅스는 `0`(그대로 비교)이라 **맥에서만 통했다**.

**확인**
```bash
sudo mysql -e "SELECT @@lower_case_table_names; SHOW TABLES FROM dotoree;"
```

**해결** — V1 의 테이블명 52곳(CREATE 18 + REFERENCES 34)을 소문자로 (ADR-045).
V1 이 바뀌면 Flyway 체크섬이 어긋나므로 맥·EC2 의 빈 DB 를 각각 `DROP DATABASE` → `CREATE DATABASE` 하고 재적용.
**jar 도 다시 빌드한다** — `V1__init_schema.sql` 은 리소스라 jar 안에 들어 있다.

**규칙**
- 500 은 고정 문구라 화면에 원인이 없다 (ADR-012). 원인은 `journalctl -u dotoree -n 80 --no-pager` 의 마지막 `Caused by:`
- 에러가 반복되면 `Restart=always` 가 5초마다 재시도하며 로그를 태운다 — 원인을 볼 땐 먼저 `sudo systemctl stop dotoree`
- **DB 를 갈아엎을 땐 앱부터 멈춘다.** 붙어 있는 DB 를 지우면 커넥션 풀이 에러를 뱉으며 재시작 루프를 돈다
- `DROP DATABASE` 는 그 DB 에 준 권한을 회수하지 않는다 — `SHOW GRANTS` 로 확인만 하면 재부여가 필요 없다
- 환경이 늘면 **"맥에서 됐다"가 근거가 되지 않는다.** 리눅스에서 쿼리를 돌리는 게이트(4단계)가 이 종류를 막는다

## 13. CD 첫 실행 — `Not authorized to perform sts:AssumeRoleWithWebIdentity`

**증상** — 1차 배포 3-6. deploy 잡의 "AWS 임시 자격 받기" 가 12회 재시도 후 실패. 3회 연속.
AWS 콘솔로 공급자·audience·역할 ARN·신뢰 정책 `aud`/`sub`/Principal 을 전부 대조했는데 **다 맞았다**.

**원인** — GitHub 이 보내는 `sub` 에 계정·저장소 **숫자 ID** 가 박혀 있었다.
`repo:<OWNER>@<OWNER_ID>/<REPO>@<REPO_ID>:ref:refs/heads/main`. 콘솔이 역할을 만들 때 자동으로 채워준 값은 이름 형태(`repo:<OWNER>/<REPO>:ref:...`)뿐.
이름은 바꾸거나 재생성할 수 있고 ID 는 불변이라 ID 형태가 더 안전하다 — AWS 의 거절은 정상 동작이었다.

**확인** — 시크릿은 로그에서 `***`, 액션의 `with:` 블록은 접혀 있어 밖에서 볼 방법이 없다. 임시 스텝으로 토큰 payload 의 클레임과 ARN **길이**만 찍었다(토큰 자체는 미출력).
`ARN 길이 = 51` 한 줄로 "시크릿이 틀렸나" 의심이 끝났고, `sub` 한 줄로 원인이 나왔다. 확인 후 스텝 삭제.

**해결** — 신뢰 정책 `sub` 를 `StringEquals` 배열로 두 형태 모두 허용. 둘 다 이 저장소의 main 으로 좁혀져 있어 느슨해지지 않는다.

**규칙**
- 이 에러는 "GitHub 은 토큰을 줬고 AWS 가 거절했다" 는 뜻 — **권한 정책이 아니라 신뢰 정책** 쪽만 보면 된다
- AWS 는 **역할이 존재하지 않아도 같은 메시지**를 준다(존재 여부를 숨기려는 설계). ARN 오타·끝의 줄바꿈도 같은 증상
- 콘솔·예제가 **자동으로 채워준 값이 실제로 오는 값과 다를 수 있다** — 실물을 찍어서 본다
- 밖에서 안 보이는 값이 의심되면 추측을 늘리지 말고 **길이·접두/접미·파싱된 필드**를 찍는다. 비밀 자체는 찍지 않는다

## 14. 호스트 키 고정 직후 — `No ED25519 host key is known … Host key verification failed`

**증상** — `known_hosts` 를 미리 쓰고 `StrictHostKeyChecking=yes` 로 바꾼 첫 실행(CI #50)에서 `scp` 가 접속 거부.

**원인** — Secret `EC2_HOST_KEY` 에 **엉뚱한 값**이 들어가 있었다. 키를 `pbcopy` 로 복사한 뒤, 길이를 확인하려고 채팅에서 `pbpaste | wc -c` 를 **복사하는 순간 클립보드가 그 명령문으로 덮어써졌다.** 확인 결과가 계속 `15` 였던 이유 — 그 명령문이 정확히 15글자다.
ssh 는 `known_hosts` 의 형식이 틀린 줄을 **에러 없이 무시**하고 "키를 모른다"고만 말해서 값이 틀렸다는 게 안 보였다.

**해결** — 복사와 확인을 한 줄로: `… | tr -d '\n' | tee >(pbcopy) | wc -c` → `80` 이 출력되고 클립보드는 유지된다. 그 뒤엔 **다른 걸 복사하지 않고** 바로 붙여넣는다.
워크플로엔 상시 검사를 남겼다 — `ssh-keygen -l -f known_hosts` 실패 시 길이(정상 80)·앞 11글자를 찍고 중단.

**규칙**
- 값은 `ssh-keyscan` 이 아니라 **이미 검증된 연결 안에서** 꺼낸다(내 `known_hosts`, 또는 SSH 로 들어가 `/etc/ssh/ssh_host_ed25519_key.pub`). keyscan 은 검증하려는 걸 검증 없이 받아온다
- 서버를 새로 만들면 지문이 바뀌어 배포가 멈춘다 — 고장이 아니라 검증이 일한 것. Secret 갱신
- 클립보드로 값을 옮길 땐 **확인 명령을 따로 복사하지 않는다**

## 15. `reset-all.sh` 가입 400 "요청 형식이 올바르지 않습니다" — zsh 가 `!"` 를 먹었다

**증상** — 4-2 회귀 직전, 새 터미널에서 `export QA_PASSWORD="<값>!"` 을 치자 `dquote>` 프롬프트가 떴다. `"` 를 한 번 더 쳐서 닫고 `sh qa/reset-all.sh` 를 돌리니
초기화는 되는데 `❌ 가입 실패 test@test.com (400)  → 요청 형식이 올바르지 않습니다.`

**원인** — zsh 는 **큰따옴표 안에서도 `!` 를 히스토리 확장**으로 본다. 그중 `!"` 는 "이 줄의 히스토리 확장을 끈다"는 특수 표기라 **두 글자가 통째로 사라진다.**
닫는 따옴표가 없어져 `dquote>` 가 떴고, 다음 줄에서 닫는 사이에 **줄바꿈이 값에 들어갔다.** JSON 문자열 안엔 날것의 줄바꿈이 올 수 없어서 Jackson 이 파싱에 실패했다.

**어떻게 좁혔나** — 응답 문구로. `"요청 형식이 올바르지 않습니다."` 는 `HttpMessageNotReadableException` 핸들러 하나만 내는 문구다 —
컨트롤러·`@Valid`·서비스까지 가지도 못했다는 뜻. 이메일 중복이면 409 `"이미 사용 중인 이메일입니다."`, 비번 규칙 위반이면 `@Valid` 메시지가 나온다.
(직전에 `유저수 0` 이 찍혔으니 중복일 수도 없었다.) **이 문구가 보인 것 자체가 같은 날 고친 `signup()` 본문 출력 덕이다** — 11번 때는 `(400)` 만 보고 헤맸다.

**해결** — 작은따옴표로 넣고 길이를 확인한다.
```bash
export QA_PASSWORD='<값>'
printf '%s' "$QA_PASSWORD" | wc -c          # 기대한 글자 수인가
printf '%s' "$QA_PASSWORD" | xxd | tail -1  # 끝에 0a 가 있으면 줄바꿈이 들어간 것
```
DB 는 유저 0명인 반쪽 상태였으므로(초기화는 됐고 가입만 실패) `reset-all.sh` 부터 다시 돌렸다.

**규칙**
- 셸에 비밀번호·토큰을 넣을 땐 **작은따옴표.** 큰따옴표는 `!`·`$`·백틱을 해석한다
- `dquote>` 가 뜨면 닫지 말고 `Ctrl+C` — 닫으면 줄바꿈이 값에 들어간다 (11번의 `dquote>` 와 같은 신호)
- 환경변수는 **터미널 창마다 따로**다. 새 창에선 `export` 도 `cd` 도 다시
- 400 의 원인은 상태 코드가 아니라 **문구**가 말해 준다 — 핸들러마다 문구가 달라서 어느 계층에서 막혔는지 알 수 있다
- 대화형 스크립트의 `(y/N)` 은 입력이 화면에 보인다. `Enter password:` 와 순서가 밀려 비번을 거기에 치면 터미널·붙여넣은 로그에 남는다 → CI 는 `QA_RESET` 으로 이 프롬프트가 없다

## 16. Nginx 설정 파일이 오염된 줄 알았다 — 채팅창이 `www.` 를 링크로 바꿔 보였다

**증상** — heredoc 으로 Nginx 설정을 쓴 뒤 `grep -n server_name` 출력을 채팅에 붙이자 `server_name dotoree.app [www.dotoree.app](https://www.dotoree.app);` 로 보였다.
`nginx -t` 는 통과(`server_name` 은 아무 문자열이나 받는다). 파일이 마크다운 링크로 오염됐다고 판단하고 `sed` 로 고쳤는데, 고친 **직후** grep 출력도 같은 모양이었다.

**원인** — 파일은 멀쩡했다. **채팅 입력창이 붙여넣은 글의 `www.…` 를 링크 문법으로 바꿔 보여준 것.** 사람이 친 명령(`-H "Host: www.$D"`)까지 같은 모양으로 보인 게 결정적 단서였다.

**두 번째 오판** — "파일에 `[` 가 있나" 를 `grep -c '\['` 로 셌더니 2 가 나와 다시 오염을 의심했다. 설정엔 원래 `listen [::]:80` (IPv6 표기) 두 줄이 있다. **검사가 찾는 글자가 정상 내용에도 있으면 검사가 아니다.**

**해결** — 정상 설정엔 절대 나올 수 없는 조각으로 센다: `grep -c '](' 파일` = 0. 줄 번호로 확인할 땐 `grep -n '\[' 파일` 이 4·12번(`[::]`)만 나오는지.

**규칙**
- 채팅에 붙인 출력은 **표시가 바뀌었을 수 있다.** 파일 내용을 판단할 땐 문제의 글자가 화면에 안 나오는 검사(개수·해시·줄 번호)로
- 검사용 패턴은 "정상일 때 0" 이 되는 것을 고른다
- 명령에 `www.` 를 직접 쓰기 꺼려질 땐 `D=dotoree.app` 후 `www.$D` (셸이 실행 때 조립)

## 17. HTTPS 를 붙였는데 리다이렉트가 `Location: http://…`

**증상** — 5-3 직후 `curl -sI https://dotoree.app` 이 `302` + `Location: http://dotoree.app/views/main.html`. 브라우저에선 멀쩡했다.

**원인** — `브라우저 ─https→ Nginx ─http→ 앱`. 암호화는 Nginx 가 풀고 앱은 평범한 http 요청을 받으니 자기 주소를 `http://` 로 만든다.
Nginx 가 `X-Forwarded-Proto: https` 를 보내고 있었지만 Spring 은 기본으로 이 헤더를 **믿지 않는다**(아무나 위조할 수 있어서).
브라우저가 멀쩡했던 건 `.app` 의 **HSTS preload** 가 `http://` 를 받는 즉시 몰래 https 로 바꿔서다 — 브라우저가 버그를 가렸고 curl 이 드러냈다.

**해결** — `server.forward-headers-strategy: native` (공통 `application.yml`). Tomcat 이 **내부 주소(127.0.0.1·사설 IP)에서 온** `X-Forwarded-*` 만 받아들인다. 앱에 직접 닿는 건 Nginx 뿐이고 Nginx 가 값을 `$scheme` 으로 덮어써서 위조가 통하지 않는다.
- 로컬 사전 확인 — `curl -sI -H 'X-Forwarded-Proto: https' http://localhost:8080/` 이 `https://` 로 돌려주면 설정이 먹은 것
- 배포 후 `Location: https://dotoree.app/views/main.html`

**규칙**
- 리버스 프록시 뒤의 앱은 "원래 요청이 무엇이었나" 를 헤더로만 안다 — 프록시를 세우면 앱이 그 헤더를 믿게 하는 설정이 짝으로 따라온다
- 브라우저 확인만으로 끝내지 않는다. HSTS·캐시·자동 보정이 서버 문제를 가린다 → `curl -sI` 로 원본 헤더
- 그대로 뒀다면 절대 URL(소셜 로그인 콜백·메일 링크)과 `Secure` 쿠키가 틀어졌다

## 18. `backup.env` 형식 검사가 0 — 안내문 예시의 `…` 를 그대로 적었다

**증상** — 5-5 에서 `/etc/dotoree/backup.env` 에 버킷 이름을 nano 로 적은 뒤 형식 검사 `grep -Ec '^S3_BACKUP_BUCKET=dotoree-prod-db-backup-[0-9]{12}-ap-northeast-2-an$'` 이 `0`, 변수 길이 `42`(기대 53).

**원인** — 안내문에 예시로 쓴 `dotoree-prod-db-backup-…-ap-northeast-2-an` 이 그대로 들어갔다. `…` 는 한 글자라 22 + 1 + 1 + 18 = 42 — 12자리 계정 ID 자리를 말줄임표가 차지했다.
스크립트를 교체하기 **전에** 잡았다. 그대로 갔다면 업로드가 실패하고(로컬 사본은 설계대로 남는다) 원인을 찾는 데 한 바퀴를 더 돌았다.

**해결** — 값을 옮겨 적지 않고 **규칙으로 조립**했다. 계정 리전 네임스페이스 버킷 이름은 `접두사-계정ID-리전-an` 이고 계정 ID 는 서버가 역할로 안다.

```
ACCT=$(sudo /snap/bin/aws sts get-caller-identity --query Account --output text)
echo "S3_BACKUP_BUCKET=dotoree-prod-db-backup-${ACCT}-ap-northeast-2-an" | sudo tee /etc/dotoree/backup.env > /dev/null
unset ACCT
```

셸 기록엔 `${ACCT}` 글자만 남는다. `tee` 는 기존 파일에 쓰기만 해서 권한(600 root)도 그대로.

**규칙**
- 규칙으로 만들어지는 값은 복사하지 말고 조립한다 — 오타가 날 자리가 없다
- 식별자를 파일에 넣었으면 **값을 화면에 드러내지 않는 검사**(정규식 개수·길이·끝 몇 글자)로 확인한다. 16번의 "정상일 때 0" 과 짝 — 여기선 "정상일 때 1"
- 안내문 예시엔 **그대로 쓰면 안 되는 게 분명한 자리표시**(`<ACCOUNT_ID>`)를 쓴다. `…` 는 그럴듯해 보여서 그대로 들어간다

## 19. 복구 리허설에서 `gzip: can't stat` — Safari 가 받자마자 `.gz` 를 풀었다

**증상** — S3 콘솔에서 `dotoree-….sql.gz` 를 Safari 로 받고 `gzip -t dotoree-….sql.gz` → `can't stat … No such file or directory`. 이어진 `CREATE DATABASE` 는 성공해서, 빈 DB 에 행 수 쿼리를 돌리자 `ERROR 1064 … near 'NULL'` 까지 났다 — 쿼리가 틀린 게 아니라 테이블이 없어 만들어질 쿼리가 NULL 이었다.

**원인** — `~/Downloads` 엔 `.sql`(26KB)만 있었다. 받은 `.gz`(3.6KB)를 Safari 가 **자동으로 풀었다**("다운로드 후 '안전한' 파일 열기" 설정으로 보인다).

**해결** — `tail -1 파일.sql` 이 `-- Dump completed on …` 인지 확인(풀린 파일도 끝까지 온전한가) → `mysql -u root -p dotoree_restore_test < 파일.sql`. 19테이블 행 수가 운영과 일치.

**규칙**
- 받은 파일은 이름을 가정하지 말고 `ls` 로 확장자부터 본다
- 첫 명령이 실패하면 뒤 명령의 에러는 **곁가지일 수 있다**(1064 는 결과였지 원인이 아니었다). 제일 위 에러부터 본다
- 실제 사고 때 헤매지 않게 복구 절차에 `.sql` / `.sql.gz` 두 경우를 적었다 — 리허설이 찾아낸 것

## 20. 무료라던 기능이 화면에선 유료 — 계획이 두 번 뒤집혔다

- 확인 전에 세운 계획은 "가정"으로 말한다 — 두 번째 번복부터는 신뢰 비용이 된다

## 21. `sudo sha256sum < 파일` 이 Permission denied — 리다이렉트는 sudo 밖에서 열린다

**증상** — 설치한 스크립트(root 700)의 해시를 `sudo sha256sum < /usr/local/sbin/dotoree-backup` 으로 보려 하자 `-bash: …: Permission denied`, 해시는 빈 값.

**원인** — `<` `>` `>>` 는 **명령이 실행되기 전에 지금 셸(ubuntu)이 연다**. sudo 가 붙는 건 `sha256sum` 뿐이라 ubuntu 가 root 700 파일을 열려다 실패. `sudo echo x >> 파일` 이 안 되는 것과 같은 함정(그래서 `| sudo tee -a` 를 쓴다).

**해결** — 파일을 sudo 쪽 명령의 **인자로** 넘긴다: `sudo sha256sum /usr/local/sbin/dotoree-backup`. 앞 12자리가 맥 `shasum -a 256 < ops/…` 와 일치.

**규칙**
- root 파일을 읽을 땐 `sudo 명령 파일`, 쓸 땐 `… | sudo tee [-a] 파일`. 리다이렉트를 sudo 뒤에 두지 않는다
- 오류 뒤에 빈 값이 나오면 "해시가 다르다"가 아니라 "읽지 못했다"다 — 비교 전에 에러 줄부터

## 22. Refresh 발급을 붙이자 CI 에서만 탈퇴 파기가 실패 — 새 FK 테이블을 파기 순서에 안 넣었다 (2026-09-27)

**증상** — `95cbde9`(Refresh 발급 + 로그인 연결) push 후 CI #64 의 qa 가 `test-withdraw.sh` 19/22 로 실패, deploy 는 건너뜀. `4-c expected [0 0 0] got [1 4 1]`(계정·카테고리·거래가 그대로) · `4-e` 파기 후 로그인 200 · `4-f` 같은 이메일 재가입 409. 로컬에선 `test-mypage.sh` 24/24 로 통과했었다.

**원인** — 로그인마다 `refresh_tokens` 에 줄이 생기는데, 이 테이블은 V1 부터 `FK_TOKEN_USER → users` 다. `purgeUser` 가 `users` 를 지우는 순간 FK 1451 → 계정 단위 트랜잭션이 통째로 롤백(`1 4 1`). `UserMapper.xml` 주석에 "users 를 참조하는 테이블을 쓰기 시작하면 여기에 추가" 라고 적어 뒀지만 발급 때 챙기지 못했다. 로컬은 파기 묶음(4-c~4-f)이 SKIP 이라 못 봤다.

**해결** — `UserMapper.deleteRefreshTokensOf`(`DELETE FROM refresh_tokens WHERE user_num = ?`, 폐기 여부 무관 전부)를 추가하고 `purgeUser` 에서 `deleteUser` 앞에 부른다. 로컬 `DOTOREE_PURGE_CRON="*/2 * * * * *"` + `QA_PURGE_FAST=1 bash qa/test-withdraw.sh` 로 22/22.

**규칙**
- `users` 를 참조하는 테이블에 **처음 INSERT 하는 커밋**에서 파기 순서(`UserMapper.xml` ★ 주석)를 같이 고친다 — 남은 후보: `auth_verifications` · `social_accounts` · 공동 가계부
- 파기처럼 로컬에서 SKIP 되는 경로를 건드렸으면 CI 와 같은 설정(별도 Run Configuration)으로 로컬에서도 한 번 돌린다
- 게이트가 운영을 지켰다 — 이 버그는 운영에 나갔다면 탈퇴자 데이터가 30일 뒤에도 영원히 남는(처리방침 위반) 조용한 실패였다
