## 깊게 판 것

설계 결정은 이유·대안·감수한 점을 [ADR](docs/decisions.md) 로 남깁니다(68개). 그중 네 가지입니다.

### 1. 잔액을 저장하지 않고 계산한다 — [ADR-065](docs/decisions.md), [066](docs/decisions.md)
- **문제** — 계좌마다 잔액 칸을 두면 거래를 고치거나 지울 때마다 잔액도 같이 고쳐야 하고, 한 곳만 빠져도 숫자가 어긋난다
- **해결** — 잔액 = 시작 잔액 + 수입 − 지출 + 받은 이체 − 보낸 이체. 기록 하나만 진실로 두고 계산은 서비스 메서드 하나 + SQL 하나에만. 이체 · 잔액 보정은 테이블을 따로 둬 통계 쿼리는 그대로
- **결과** — 잔액이 기록과 어긋날 수 없고, "그날 기준 잔액"도 날짜 조건 하나로 나온다. 느려지면 계산 한 곳의 안쪽만 "월말 스냅샷 + 그 뒤 합"으로 바꾼다

### 2. 훔친 로그인 토큰을 다시 쓰면 그 로그인 전체를 끊는다 — [ADR-055](docs/decisions.md)
- **문제** — Refresh 토큰을 쓸 때마다 새 것으로 바꿔도, 서버는 옛 토큰을 들고 온 쪽이 도둑인지 주인인지 알 수 없다
- **해결** — 로그인 한 번에서 이어진 토큰들을 한 묶음으로 두고, 이미 쓴 토큰이 다시 오면 묶음 전체를 폐기. 응답 유실 · 탭 두 개 동시 갱신은 30초 유예. "이미 썼나 확인 → 바꾸기"를 `UPDATE … WHERE revoked_yn='N'` 한 문장으로 합쳐 동시 요청이 끼어들 틈을 없앴다. 401 을 던져도 폐기는 커밋되게 `noRollbackFor`
- **결과** — 도둑이 토큰을 한 번 쓰면 주인 쪽 다음 요청에서 그 로그인이 통째로 끊긴다. DB 엔 SHA-256 해시만, 쿠키는 `HttpOnly · Secure · SameSite=Strict`

### 3. "맥에서만 통하던" 쿼리를 배포 전에 잡는다 — [트러블슈팅 12](docs/트러블슈팅.md), [ADR-064](docs/decisions.md)
- **문제** — 첫 배포 때 EC2 에서만 `Table 'dotoree.users' doesn't exist`. 원인은 `lower_case_table_names`(맥 2, 리눅스 0). 그때 CI 는 쿼리를 한 번도 실행하지 않았다
- **해결** — CI 에서 운영과 같은 MySQL 8.4 를 일회용으로 띄워 통합 테스트를 돌리고, 하나라도 실패하면 배포를 멈춘다
- **결과** — JUnit 200여 개가 배포 전 관문. 새 기능이 탈퇴 데이터 파기와 FK 로 부딪힌 문제도 운영에 나가기 전에 잡았다

### 4. 백업은 "복원까지 해야 끝" — [ADR-050](docs/decisions.md)
- **문제** — 매일 백업 파일이 쌓여도, 덤프가 중간에 잘렸거나 복원이 안 되면 없는 것과 같다
- **해결** — 서버는 S3 에 넣기만 하고(읽기 · 삭제 권한 없음), 잘린 덤프를 흉내 내 완료 검사를 실측, 별도 DB 에 복원 리허설. 백업이 실패하거나 끊기면 CloudWatch 경보
- **결과** — 서버가 털려도 지난 백업은 지울 수 없고, 복원이 되는 것까지 확인한 백업만 남는다

**그 밖에** — GitHub 에 장기 키 없이 OIDC 1시간 임시 자격 · 배포할 때만 22번 포트 열기([ADR-042](docs/decisions.md), [048](docs/decisions.md)) · 새 마이그레이션은 이전 jar 로 롤백해도 돌아가게([ADR-053](docs/decisions.md)) · 반복 예정은 `(rule_num, scheduled_date)` UNIQUE 로 두 번 눌러도 거래 한 줄([ADR-067](docs/decisions.md)) · 문의 메일도 국내(SES 서울 → S3)에 보관([ADR-056](docs/decisions.md))

```mermaid
flowchart LR
    U[브라우저] -->|HTTPS| N[Nginx<br/>80→443, /actuator 차단]
    N --> A[Spring Boot<br/>정적 화면 + /api JSON]
    A --> D[(MySQL)]
    D -. 매일 04:00 덤프 .-> S3B[(S3 백업<br/>30일 보관)]
    M[문의 메일] --> SES[SES 수신 · 서울] --> S3M[(S3 메일함<br/>90일 보관)]
```

- 화면과 API 를 한 프로세스가 서빙합니다(별도 프론트 서버 없음). 계산·판단은 서버, 화면은 표시만 합니다.
- `main` 에 push 하면 **JUnit 단위·통합 테스트 200여 개**가 일회용 MySQL 에서 돌고, 그 빌드의 jar 를 한 번 띄워 헬스 200 을 확인한 뒤 배포합니다. 하나라도 실패하면 배포되지 않습니다.

## 로드맵

> 지금은 **Sprint 1(개인 가계부 + 계좌 · 잔액 + 인증 + 배포·운영)** 단계입니다. 영수증·결제내역 캡처 AI 분석(Sprint 2~3)은 설계를 마치고 순서대로 만들고 있습니다.

- **Sprint 1 마무리** — 화면 다듬기, Access 토큰 메모리 보관, 실무 표준 정리(PATCH · Swagger · record · enum · ETag), 시각 UTC 저장
- **Sprint 2** — Clova OCR, 업로드(사진은 저장하지 않음), 정규식 1차 파싱 + LLM 보완, AI 분석 중 DB 커넥션을 잡지 않는 트랜잭션 분리
- **Sprint 3** — 상호명 임베딩 검색으로 카테고리·메모 추천, 정확도 전후 비교
- **Sprint 4** — API 호출 제한(앱 + Nginx), 전체 점검

## 협업 방식

AI 와 페어로 개발합니다. 무엇을 · 왜 만들지는 제가 정하고 ADR 로 남기며, 구현은 AI 에 맡기고 diff · 테스트로 검토합니다. 모든 결정의 "왜"를 제 말로 설명할 수 있게 하는 것이 기준입니다.
